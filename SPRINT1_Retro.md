## PipilinePal - Sprint 1 Retrospective 

### What went well 

 . Writing the date model as plain, testable     functions ( createboard , createCard)
 before touching any UI meant I could verify Story 1 as actually correct in the browser console before building anything on top of it - no guessing.

 . Keeping the first working version in one plain HTML file with no build tools meant zero setup friction. I could test behavior (a button click, a rendered column) within minutes instead of losing time to toolng.

 ## What didn't go well 

  . I significantly underestimated how much scaffolding I needed before I could do any " real" Sprint 1 work - the project had planning docs but zero code, so Task 5 required setting up a working page from nothing rather than just picking up an existing task....

  . I somehow loste time going back and forth on what language to use for real work ( react vs plain js vs C#) before settling on plain HTML/JS, which was the right call for where the project actually was .

  ## Concrete change for Sprint 2.

  Before Sprint 2 planning starts, confirm the actual state of the codebase first (what files exist, what's already running) instead of assuming the stack decided on paper is already reflected in real files. I spend the first 10 minutes of sprint 2 planning literally opening the project nd checking what's real before writing any new stories.
